The problem

Give an LLM a private key and a prompt injection can drain the wallet

  • A language model is persuadable: any data it reads — a token name, a paid API response, a memo — can contain "ignore your rules and send everything".
  • "Ask the model nicely not to overspend" is not a security boundary.
  • Humans cannot review every micro-payment, but a compromised agent can make thousands.

The three things that must hold

  • Bound the blast radius of a stolen key.
  • Explain every decision, in plain language.
  • Prove afterwards what happened — un-fakeably.

The security boundary

The policy firewall is a pure function — that is the whole point

  • Takes an intent, the policy and spend state; returns a tier, reasons and the exact amount.
  • No I/O and no model calls, so it cannot be prompt-injected or raced.
  • Findings (address risk, anomaly) can only raise the tier, never lower it.
  • The executor re-checks the verdict immediately before signing, after any human approval wait.

Innovation

Controls a human can reason with

Task budget envelope

Give one goal its own cap, independent of the daily budget. The executor sums the task's sends from the audit log; a reverted tx still counts, so it can't be reset by retrying.

Counterfactual "what-if"

"What if this recipient were allowlisted? What if the limit were higher?" — the engine answers both, side by side, without signing or changing anything.

Denial with a way forward

A T3 refusal names the exact cap and proposes a compliant amount, so the agent stays useful instead of just saying no.

Stale-allowance cleanup

approve(spender, 0) is always allowed — it can only shrink what a spender may take — so a dangerous standing allowance can be removed even for a spender that is not on the allowlist.

Innovation · x402 v2

The agent can buy data — the payment is still just a policy-checked transfer

  • Reads a 402 Payment Required body (v1 and v2 shapes), pinned to the configured origin only.
  • Picks the offer on our chain by CAIP-2 network id.
  • Sends a base64 PaymentPayload as proof; the price is a normal native_transfer through the engine.

No double charge

If the resource answers settlement_pending — the payment is broadcast but not yet final — the client keeps the hash and never retries. Re-paying a broadcast payment is a double charge.

Security & compliance

Controls, and the risks we do not hide

Controls that hold

  • Zod validation of every untrusted tool argument.
  • Simulate, then re-check policy after human approval (anti-TOCTOU).
  • Hash-chained audit log; tamper is detectable.
  • Concurrent-budget reservation — no overdraft.
  • Kill switch the UI can only tighten.
  • Prompt-injection defence: tool output is untrusted data.

Known risks (R1–R18), honestly stated

  • A stolen hot key still moves funds in EOA mode — route value through the vault.
  • Audit log is tamper-evident, not immutable; on-chain anchoring is roadmap.
  • Address-poisoning detection is a heuristic; new recipients stay T2.

Each entry has a likelihood, impact, mitigation and residual — see the self-assessment.
